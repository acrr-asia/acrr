# Maintenance

## Changing the house style

1. Change the standards manual first (`publication.standards`), with a line in its change log. The manual is the authority; rules implement it.
2. Change the rule: a severity in `rules`, a threshold in `thresholds`, a term or phrase in the glossary, or a language setting in `language`.
3. Run `eos lint` across the corpus and look at what the change catches before raising a rule to `error`. A rule with false positives on real content belongs at `warning` until it is fixed.
4. If the fix is mechanical and safe everywhere, add `replace` to the glossary term and run `eos fix --rules terminology`. Read the diff before committing.
5. A change that edits published files makes their records stale; they need a review of the changed passages and a new `eos record` before the gate passes again. Plan style changes as a batch for that reason.

The `style-guide` skill performs these steps and records the decision.

## Adding a term

In `editorial/glossary.json`:

```json
{ "prefer": "time step", "avoid": ["\\btimestep(s?)\\b"], "replace": "time step$1", "note": "Two words, as in the numerical-methods literature." }
```

`avoid` entries are regular expressions matched against prose only (code, math, JSX, URLs and front-matter keys are masked). Add `caseSensitive: true` for terms like product names, and `scope: "body"` to skip titles and front matter. Always give a `note`: it is shown with every finding.

## Adding a content type or a site

Add an entry to `content.types` with its globs, route pattern and required fields, then a `review.requiredStages` and `review.minimumTotal` entry for it. Run `eos inventory` to confirm every file is found and every route matches a built page.

## Adding a rule to the engine

Rules live in `lintItem` in `scripts/eos.mjs`. Each finding has a rule id, severity (from `rules` in the config, with a default), line, message and, where useful, a suggestion. Keep the engine dependency-free. Before raising a new rule's default to `error`, run it on a real corpus and record the false-positive rate in the CHANGELOG entry.

## Upgrading

- Plugin: bump `version` in `.claude-plugin/plugin.json` (the engine reads its version from there), add a CHANGELOG entry, run `claude plugin validate plugins/editorial-os`.
- Record format: records carry `schema: "eos-review-record/1"`. A breaking change needs a new schema id and a migration in `readRecord`, never a silent reinterpretation of old records.
- Site generator upgrades: re-run `eos validate-site` on a fresh build. Rendering checks depend on the HTML the generator emits (KaTeX class names, heading markup).

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Gate fails with `review-stale` after a small edit | Intended: the content hash changed. Review the change and run `eos record` again |
| `eos lint` flags a technical term as a spelling variant | Add the word to `properNouns` or narrow the variant list in `data/spelling-variants.json`; never weaken the rule globally |
| `validate-site` reports duplicate ids generated by a library (for example Mermaid actors) | Add a pattern to `validation.site.ignoreDuplicateIds` with a comment saying where they come from |
| `eos syntax` says the MDX compiler is missing | Run it from the project root after `npm install`; it uses the project's own compiler on purpose |
| Hook prints nothing | It only reports for files matched by `content.types` globs and not excluded; check with `eos lint <file>` |
| `check-external` reports "not verified" | The host was unreachable from this machine. That is not "broken"; check again elsewhere before changing the link |

## Periodic tasks

- Each release: `eos status` should show every published item `ready`.
- Monthly or before a large release: `eos check-external` (when the site has external links), `eos refs` to spot inconsistent citations, and a sample re-review of the oldest records.
- After a series is completed or changed: the series review (ACRR: `scripts/series-pipeline.mjs`).
