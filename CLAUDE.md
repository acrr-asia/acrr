# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ACRR (Advanced Computing & Robotics Research): a static research/technical publishing site, written in English with Vietnamese translations under `/vi`. Six sections: Home, Blog, Series, Learning, Insights, About. [idea-plan.md](idea-plan.md) is the source of truth for scope and requirements (read it before changing behaviour); [README.md](README.md) is the user-facing guide for install, authoring, SITE_URL and deployment. The articles, series and insights in the repo are published content (none is `example` or `draft`); no biography or contact details have been supplied. Production is GitHub Pages at https://acrr.asia (`.github/workflows/deploy.yml` on push to `master`, `public/CNAME`).

Stack: **Astro 7** (not 5; if an API looks unfamiliar read `node_modules/astro/dist` or its `.d.ts` files rather than guessing), MDX, TypeScript strict, content collections, remark-math + rehype-katex, Shiki, `@astrojs/sitemap`, `@astrojs/rss`, Pagefind. Requires **Node >= 22.12** (Astro 7's engines field) and Playwright's Chromium (`npx playwright install chromium`, once) because Mermaid diagrams are rendered at build time. No UI framework, no external fonts or CDNs. There is no test framework: verification is the build plus the link checker.

## Commands (all verified)

```sh
npm install
npm run dev            # dev server, http://localhost:4321; drafts visible; search does NOT work (no index yet)
npm run build          # astro check && astro build && pagefind --site dist && check-site-url   (the full release check; works locally without SITE_URL, which only warns; set SITE_URL for deployable builds, see Gotchas)
npm run build:local    # same, but localhost URLs in the sitemap/RSS never fail the build (warning only, even in CI); never deploy its dist/
npm run preview        # serve existing dist/ (run build first); search works here
npm run check          # astro check only (types + templates; fast)
npm run check:links    # node scripts/check-links.mjs [distDir] — needs a built dist/
npm run check:site-url # node scripts/check-site-url.mjs [distDir] [--allow-localhost] — needs a built dist/
```

Release check: `SITE_URL=https://<real-origin> npm run build && npm run check:links`. Both must exit 0. Without `SITE_URL`, a plain `npm run build` on a local machine exits 0 and prints a warning (the sitemap and RSS contain `localhost`; `dist/` is fine for `npm run preview`, not for deployment). In a recognised deploy environment (`CI`, `GITHUB_ACTIONS`, `NETLIFY`, `CF_PAGES` or `VERCEL` set) the same missing `SITE_URL` exits 1 at the `check-site-url` step; a CI smoke test that is not a deployment uses `npm run build:local` (or `ALLOW_LOCALHOST_BUILD=1`).

Checking one page or link:

- There is no per-page build. After `npm run build`, open the page via `npm run preview` (e.g. `/blog/feedback-and-system-behavior`), or inspect the file directly (`dist/blog/feedback-and-system-behavior.html`; `grep` it for the text you expect).
- `check:links` always scans the whole site (well under a second); filter its output by page or URL. It resolves links the way a static host does, validates `#fragment` targets against ids in the target page, ignores external URLs and `/pagefind/`, and checks absolute URLs under `SITE_URL` if that env var is set.
- To build without touching `dist/` (for experiments): `npx astro build --outDir <scratch-dir>`, then `node scripts/check-links.mjs <scratch-dir>`. `SITE_URL=https://example.com npx astro build --outDir <dir>` verifies canonical/sitemap/RSS output, and `node scripts/check-site-url.mjs <dir>` runs the localhost guard on it.
- A preview/dev server started in the background can outlive the shell that started it. Stop a preview server with `npx astro preview stop` (or start with `--force`); a dev server has to be killed by PID.

## Architecture

- `src/content.config.ts`: all collection schemas and the `CATEGORIES` enum (the frontmatter contract). Collections: `blog` (glob `src/content/blog/**/*.{md,mdx}`; `series` is a `reference('series')`, plus `seriesOrder`, `draft`, `example`), `series` (`status`, `objectives`, `plannedEntries`, `example`), `insights` (`kind` enum, `draft`, `example`), `learning` (`file('src/data/learning.json')`; every item needs an `id`; `url` optional and must be a valid URL).
- `src/lib/content.ts`: the only place that should query blog/insights/series for display: `getPosts`, `getInsights`, `getSeriesList`, `getSeriesPosts`, `getRelatedPosts`, `getTagIndex` (+ `TagEntry`, `tagSlug`), `formatDate`, `slugify`. Lists sort newest first; on the same date a higher `seriesOrder` counts as newer, then the id breaks ties. Drafts are filtered here with `import.meta.env.DEV`, so they exist in `astro dev` only. Pages must go through these helpers, never raw `getCollection('blog')`, or drafts leak into production. `getPosts` also throws if an article references a series id that does not exist.
- Pages (`src/pages`, mirrored in `src/pages/vi`; each is a thin wrapper around a view in `src/views/`, see Languages below): `index`, `about`, `learning`, `blog/index`, `blog/[...slug]` (article via `layouts/Article.astro`), `blog/category/[category]`, `tags/index`, `tags/[tag]`, `series/index`, `series/[id]`, `insights/index`, `insights/[id]`, `404`, `rss.xml.ts`. Layout shell: `layouts/Base.astro` (props: `title`, `description`, `narrow?`, `canonical?`, `ogType?`, `noindex?`, `searchable?`, `example?`), which wraps Header, Footer, `SEO.astro` and `Search.astro`. Listing pages (home, `/blog`, `/blog/category/*`, `/tags`, `/tags/*`, `/series`, `/insights`) pass `searchable={false}`; the article, insight and series-detail pages pass `example='article' | 'insight' | 'series'` when `data.example` is true (see Search and Content-integrity below).
- Article page: `layouts/Article.astro` is a two-column grid on wide screens (text column 40rem plus a sticky "Contents" `<aside>` from `components/TableOfContents.astro`, fed by the `headings` returned from `render()` and passed down from `blog/[...slug].astro`), and a plain 42rem block below 64rem (not a grid, so the sticky Contents child stays pinned for the whole article) where Contents becomes a bar pinned to the top of the window: it shows the section being read and a reading-progress line, and opens the full list as a dropdown that closes on navigation, Esc or an outside tap (the script adds `.enhanced`; without JS it is a plain open box). `prose.css` gives h2/h3 a `scroll-margin-top` on narrow screens so jumps land below the bar. The aside is skipped when an article has fewer than two h2/h3 headings and carries `data-pagefind-ignore`. Insights pages do not have it. Every article also gets `components/ArticlePager.astro` (older/newer by publication date, `rel=prev/next`, Example badge on sample neighbours); series articles additionally get the series block with previous/next inside the series.
- Tags: `TagList` renders each tag as a link to `/tags/<tagSlug(tag)>`; `getTagIndex()` builds the index from published articles and insights (a draft-only tag has no page; `getStaticPaths` in `tags/[tag].astro` is driven by it). `tagSlug` strips accents, maps `+`/`#` to `plus`/`sharp`, falls back to `tag-<hash>` for non-Latin tags, and reserves `index`; `getTagIndex` throws when two genuinely different tags share a slug (case/spacing variants merge on purpose). `TagNav` (`scope='posts'` on `/blog` and `'insights'` on `/insights` so counts match the list above them, `'all'` on tag pages) is the filter row; PostCard tag links need `z-index` above the stretched title link.
- Shared components: `PostCard` (`{post}`), `SeriesCard` (`{series, count}`), `InsightCard` (`{insight}`), `StatusBadge`, `TagList`, `TagNav`, `RelatedPosts`, `CategoryNav`, `PostList` (`level`, `groupByYear`), `ArticlePager`, `TableOfContents`, and `components/home/*` (including `ExploreMenu`) (research areas live in `components/home/research-areas.ts`, shared by Home and About).
- Styling: `src/styles/tokens.css` (CSS custom properties; dark mode follows `prefers-color-scheme`, no toggle), `global.css`, `prose.css`. Use tokens only; no hard-coded colours (the `theme-color` meta values in `SEO.astro` and the favicon mirror `--bg`/`--accent` because they cannot read CSS variables; update them together).
- Search: `Search.astro` is a native `<dialog>` opened by `Ctrl/Cmd+K` or any `[data-search-open]` element; it lazily imports `/pagefind/pagefind.js`. `Base.astro` puts `data-pagefind-body` on `<main>` only when the page is indexed: not for `noindex` (404) and not for `searchable={false}` (listing pages, whose content is indexed on the pages it belongs to; indexing them too gives duplicate hits and ambiguous titles such as a bare category name). Indexed pages are the articles, insights, series detail pages, About and Learning (the Pagefind build log says "Indexed N pages"; N should equal that count). UI chrome inside an indexed page (`PostCard` "Read article →" and badges, the related-articles block, the series prev/next nav, `ArticlePager`, the insight tag list) carries `data-pagefind-ignore` so excerpts read as prose. For `example` pages, `Base.astro` adds `<span hidden data-pagefind-meta="example:Example">`; `Search.astro` renders an "Example" badge from `meta.example`. `pagefind.yml` excludes `.katex-html` and `annotation` so math is indexed once. Pagefind falls back to shorter prefixes of a query word that is not on the site (a "kalman" query returns pages matching "k"), so `Search.astro` fetches up to 30 hits, keeps only those whose `data.content` contains every query term as a word prefix (plus crude inflection stems, because Pagefind stems), and computes the count and the "No results" branch from that filtered list. Esc is handled in the dialog's own keydown handler (`type="search"` otherwise eats the first Esc to clear the field).
- Path normalisation: `src/lib/path.ts` exports `publicPath(pathname)`, used by `Header.astro` (active nav), `SEO.astro` (canonical) and `Base.astro` (og:type; `/blog/category/<slug>` is a listing and gets `website`, only `/blog/<slug>` and `/insights/<slug>` get `article`). Use it for anything that reads `Astro.url.pathname`.
- `scripts/check-site-url.mjs`: post-build guard (the last step of `npm run build`, after Pagefind); when `dist/rss.xml` or `dist/sitemap*.xml` contain a localhost URL it fails in a recognised deploy environment (`CI`, `GITHUB_ACTIONS`, `NETLIFY`, `CF_PAGES`, `VERCEL`) and only warns elsewhere; `--allow-localhost` / `ALLOW_LOCALHOST_BUILD=1` (what `npm run build:local` uses) makes it a warning everywhere.
- Mermaid: ```` ```mermaid ```` blocks in any article are rendered to inline SVG at build time by `rehype-mermaid` (`astro.config.mjs`: `inline-svg`, `neutral` theme, compact flowchart/sequence spacing, `errorFallback` throws so a broken diagram fails the build; `syntaxHighlight.excludeLangs` keeps Shiki off them). `src/plugins/rehype-mermaid-figure.mjs` wraps each SVG in `figure.diagram.mermaid-diagram` (with `data-pagefind-ignore`) and sets a min-width of 60% of its natural width (the largest diagram, 983px, then fits the ~612px column); `.mermaid-svg` rules in `prose.css` recolour Mermaid's id-scoped styles with tokens (`!important` is required). `playwright` is pinned (1.56.1) and the deploy workflow runs `npx playwright install --with-deps chromium`; keep them in step. After adding a diagram type not used yet (class, state, ER...), screenshot it in light and dark mode: the overrides only cover flowchart and sequence classes.
- Diagrams: inline SVG Astro components in `src/components/diagrams/`, generated by `scripts/generate-diagrams.py` (edit the script and re-run it, do not hand-edit the output) and wrapped in `components/Figure.astro` (caption) inside `.mdx` articles. They use only the `.diagram-svg` classes in `prose.css` (token colours, so dark mode works); the SVG carries `data-pagefind-ignore`, the caption is indexed. Plot data must come from the article's own formulas.
- Reading time: `src/plugins/remark-reading-time.mjs` writes `minutesRead`; read it with `const { Content, remarkPluginFrontmatter } = await render(entry)` (`render` is imported from `astro:content`).
- `scripts/check-links.mjs`: dependency-free link checker (above).
- Series review: when a series becomes complete (`status: "published"` and no `plannedEntries`), every article in it is reviewed by the procedure in `.claude/skills/series-review/SKILL.md` (report in `reviews/<id>.md`, recommendations only; never edit articles during a review). Triggers: the `PostToolUse` hook in `.claude/settings.json` (runs `node scripts/series-review.mjs hook`, which compares the edited series file with `HEAD` and adds context only on the transition to complete) and `.github/workflows/series-review.yml` (push to `master` touching `src/content/series/`, or manual dispatch; needs the `ANTHROPIC_API_KEY` secret; opens an issue). `node scripts/series-review.mjs list <id>` / `detect <base> <head>` are the shared helpers. Full documentation: README "Automated series review".

## Languages (English original, Vietnamese translations)

- Translations live in a `vi/` subdirectory of each collection (`src/content/blog/vi/<slug>.mdx`, `series/vi/<id>.md`, `insights/vi/<id>.md`) with the original's file name; `entryLang(entry)` and `baseId(entry)` in `src/lib/content.ts` read that prefix. Every helper there takes a `lang` (default `'en'`): `getPosts('vi')` returns each original replaced by its translation where one exists, so Vietnamese listings show untranslated entries in English (badge "Tiếng Anh", link to the English page). Never build an href from `entry.id`; use `postHref`, `seriesHref`, `insightHref`.
- `pairTranslations` fails the build when a translation has no original or when a copied field differs (dates, category, tags, series, seriesOrder, draft, example; for series: status, category, example and the number of `plannedEntries`). So when an English series file changes (an entry published, a planned entry removed, the status changed), update `src/content/series/vi/<id>.md` in the same commit.
- Routing: `src/pages/**` (English) and `src/pages/vi/**` (Vietnamese) are thin wrappers that render the same view from `src/views/`; dynamic routes take `getStaticPaths` from `src/lib/routes.ts` (`blogPaths(lang)` etc.; a Vietnamese article, series or insight page exists only when translated). Components read the page language with `langFromUrl(Astro.url)` (`src/i18n/ui.ts`), so they need no `lang` prop; interface strings come from `t(lang)`, category and insight-kind labels from `categoryLabel` / `kindLabel` (stored values and URL slugs stay English). Use `localizePath(path, lang)` for every internal link in a view or component.
- `Base.astro` sets `<html lang>`, the language switcher (in `Header.astro`) and hreflang links (`SEO.astro`, only with `SITE_URL`). Pages that may lack a counterpart pass `counterpart` (the English route of the other version, or `null`). Pagefind builds one index per `<html lang>` (the build log says "Indexed 2 languages"); the search UI strings travel to the client script through the dialog's `data-ui`. `/vi/rss.xml` lists translated articles only; `check-site-url` checks it too. The sitemap integration has `i18n` set, so it pairs `/x` with `/vi/x`.
- After touching navigation, also grep `dist/vi/blog.html` etc. for `aria-current="page"`, and check a Vietnamese page at 360px (Vietnamese labels are longer).

## Gotchas

- **Astro 7 markdown config.** Remark/rehype plugins are set through `markdown.processor: unified({ remarkPlugins, rehypePlugins })` (import `unified` from `@astrojs/markdown-remark`) in `astro.config.mjs`, not top-level `remarkPlugins`. `z` comes from `astro/zod`; loaders from `astro/loaders`; entries use `entry.id` (not `slug`) and the standalone `render()`.
- **URL shape.** `build.format: 'file'` and `trailingSlash: 'never'`: files are `dist/blog.html`, `dist/blog/<slug>.html`, but public routes are extensionless (`/blog`, `/blog/<slug>`, `/series/<id>`). Never write a trailing slash or `.html` in a link. During the build `Astro.url.pathname` is `/blog.html` (dev: `/blog`), so **any component that reads `Astro.url.pathname` must strip `.html` first** with `publicPath()` from `src/lib/path.ts` (`Header.astro`, `SEO.astro` and `Base.astro` do). A raw comparison works in `astro dev` and silently fails in the production build (this is how the header's `aria-current` once went missing on every top-level section page). After touching navigation, grep `dist/blog.html`, `series.html`, `learning.html`, `insights.html`, `about.html` for `aria-current="page"`. Pagefind returns `.html` URLs; `Search.astro` strips them. Hosts must resolve `/x` to `x.html` (see README).
- **Whitespace before inline elements.** Astro's HTML compression can drop the whitespace between text and an inline element that starts on the next source line (`labelled⏎<span class="badge">` became `labelled<span ...>`, so the page read "labelledExample"). Keep text and inline element on one source line, or write `{' '}` at the end of the line. After changing copy that mixes text with `<span>`, `<strong>`, `<a>` or `<code>`, grep `dist/` for a letter or punctuation mark glued to `<span`, `<strong>`, `<a ` or `<code`.
- **Code-block colours.** Shiki's dark theme is `github-dark-default`, chosen because `github-dark` comments (`#6A737D`) are only 3.5:1 on `--code-bg` (WCAG 1.4.3 needs 4.5:1). `prose.css` paints the dark code background itself (`--code-bg`), so when changing a Shiki theme or `--code-bg`, re-check every token colour in `dist/blog/*.html` (`--shiki-dark:#...`) against `--code-bg`, and `color:#...` against the light background.
- **Drafts only in dev.** `draft: true` content appears under `npm run dev` (with a Draft badge) and nowhere in production: routes, archive, tag pages (a tag only drafts use has no page), series pages, home, RSS, sitemap, search. No draft exists at present; to test a change touching listings, add a temporary `draft: true` entry and confirm its slug and title are absent from `dist/`. `example: true` is separate: it is published but labelled.
- **Pagefind runs after Astro.** It indexes `dist/`, so `/pagefind/` exists only after `npm run build`. `npm run dev` therefore has no search, and `check-links` ignores `/pagefind/`.
- **Bad references.** Astro itself only logs an error (exit 0, even `astro check` passes) for a `series:` id that does not exist; the guard in `src/lib/content.ts` turns this into a build failure. Invalid Learning `url` values and schema mismatches fail the build natively.
- **SITE_URL.** Canonical/`og:url` are emitted only when `SITE_URL` is set; with the localhost fallback they are omitted, but the sitemap and RSS would contain `localhost` URLs. `npm run build` therefore ends with `scripts/check-site-url.mjs` (after Pagefind, so a failure never leaves `dist/` without a search index): with `SITE_URL` unset it exits 1 in a deploy environment (`CI`, `GITHUB_ACTIONS`, `NETLIFY`, `CF_PAGES`, `VERCEL`), so a deploy that forgot the variable cannot publish a localhost sitemap or feed, but only warns on a local machine so that a fresh checkout builds. `npm run build:local` / `ALLOW_LOCALHOST_BUILD=1` makes it a warning in CI too; a `dist/` built that way must not be deployed. Always set `SITE_URL` for production. No `base` path is configured; the site assumes the domain root. If you change the sitemap/RSS setup, keep the guard in step with it.
- **Windows.** Use the Write/Edit tools to create files (shell heredocs are unreliable here). PowerShell sets env vars as `$env:SITE_URL = "..."`; Git Bash as `SITE_URL=... npm run build`.
- `dist/`, `.astro/` and `node_modules/` are gitignored and regenerated.

## Content-integrity rules (easy to violate, strictly required)

- Never fabricate: founder biography, credentials, affiliations, publications, collaborators, contact details, statistics, readership/citation figures, research results, project counts, or external URLs. Missing data stays missing.
- No Notion URLs exist yet. Learning entries without a real `url` render as "Coming soon" with no link; never give them a made-up URL. Notices on the Learning page are conditional on the data, so keep them true when links are added. Keep authoring instructions (file names, field names, commands) out of visitor-facing page copy: they belong in README.md or in source comments, because every public page is also indexed by search.
- Sample/demo articles, series and insights must be labelled (`example: true`, visible "Example" badge/notice) and never presented as completed original research. The label must also survive outside the page body, where a sample is most likely to be read as real: `[Example]` in `<title>`, an "Example article/insight/series:" prefix on the meta and og description (both via the `example` prop of `Base.astro`), `[Example]` in RSS item titles (and a note in the channel description), and an "Example" badge on search results. Series and entries that are not written are "Planned".
- Research areas on Home and About are proposed interests, not claims of active projects or a staffed lab. Do not overstate ACRR's size or achievements. Any figure shown on the site must be computed from real content.
- Insights entries separate established facts, interpretations and open questions (`## Established`, `## Interpretation`, `## Open questions`).
- Do not copy text, names, taglines or articles from the reference site or any other site. All writing must be original and technically correct.
- English is the original language. Vietnamese pages are translations under `/vi` that follow `docs/translation-vi.md` (glossary, copied fields, Vietnamese term plus English term on first use); never write Vietnamese-only content. No other languages.

## Design direction

Editorial, restrained "independent technical publication" style (reference: tieukhoimai.me for information architecture and presentation only: section set, card layout, Ctrl/Cmd+K search; not its content or identity). Section labels use the `.eyebrow` pattern; article cards show date, category, title, summary and "Read article →". Long-form readability, comfortable line lengths (`--measure`), distinct styling for code, equations, quotes and diagrams, one `<h1>` per page, keyboard accessible, readable at 360px width, minimal decorative animation.
